## 1. 计划重置说明

原始 14 天计划中的 D1–D8 已完成，不再作为待开发事项；后续不重复搭建已存在的来源、解析、候选审核、知识树、Hybrid RAG 和 Citation Validation 链路。

当前路线从“可信知识生产闭环”进入“可信知识更新与学习应用闭环”：

```text
已有知识与来源
→ 外部资料研究
→ 新旧证据对比
→ 用户审批的知识更新
→ Revision 与索引
→ 问答、复习、练习、考试
→ 掌握度与薄弱项反馈
```

开发顺序遵循：先完成可审计的知识更新，再建设确定性学习数据，再补充题目/评分，最后才在真实复杂度需要时引入受控 Agent。

## 4. 重新编排的 14 天执行日程

> D1–D8 是已完成基线；以下 N2–N7 是从当前状态继续推进的 14 个开发日。每一天只设置一个主验收目标，完成后才能进入下一天。

| 日 | 主目标 | 当日交付 | 验收门槛 |
|---:|---|---|---|
| 1 | Proposal 领域基座 | `ResearchRun`、`KnowledgeUpdateProposal`、状态机、迁移和 DTO | 迁移可回放；状态迁移、空间隔离、幂等测试通过 |
| 2 | Proposal Evidence | 新旧证据关系、差异分类、冻结引用快照和业务校验 | 伪造、越范围、过期 Evidence 被拒绝 |
| 3 | Grok 搜索 Provider | 服务端 Provider Adapter、配置、错误分类、Provider 契约 | Key 不出前端；超时、429、5xx 和协议错误可控 |
| 4 | 多 URL 来源固化 | 多链接选择、抓取、SourceVersion、解析 Job 与部分失败 | 选中链接可固化；SSRF、大小、重定向防护通过 |
| 5 | 新旧内容比较 | 复用现有 Hybrid RAG 生成结构化比较结果 | 支持、补充、冲突、过时和证据不足样例通过评测 |
| 6 | Proposal 审核 API | 列表、详情、批准、拒绝、编辑和应用事务 | 批准前正式知识不变；批准后只创建新 Revision |
| 7 | Proposal 审核 UI | 对比视图、证据引用、审批弹窗、刷新恢复 | 键盘、焦点、加载/空/错误状态通过 |
| 8 | Markdown 图片附件 | 附件模型、相对路径校验、对象存储关联和展示 | 非法路径/类型拒绝；Revision 与附件稳定关联 |
| 9 | FSRS 调度 | Versioned Scheduler Adapter、迁移和 ReviewLog 重放 | 到期、忘记、重启恢复和旧卡迁移通过 |
| 10 | 学习计划与掌握度 | LearningGoal/Plan、今日任务、掌握度投影 | 原始复习/答题记录可追溯，缺失数据不伪造 |
| 11 | 练习系统 | 题目 Schema、选择/填空/简答/默写、作答保存 | 题目绑定范围、Revision、Evidence 和 rubric |
| 12 | 考试与面试 | 难度递进组卷、文本/语音转文字、成绩记录 | 断线/草稿恢复；录音不被误当作评分事实 |
| 13 | 评分与薄弱项 | Evidence/Rubric 评分、成绩趋势、专项补强任务 | 无证据评分进入复核；掌握度可重算 |
| 14 | 质量收口与发布 | 全链路 E2E、研究/QA/学习评测、文档和已知限制 | 范围越界和审批前写入为 0；关键测试与构建通过 |

若某天验收未通过，暂停新增功能，先修复当日领域边界、数据一致性或测试问题。Agent 不占用固定日期，只有 N2 Proposal 流程稳定且出现真实多步研究需求后，才在 N6 作为独立阶段启动。

## 5. N2：资料研究与知识更新

### 4.1 N2.1 研究领域模型与迁移

| 项目 | 内容 |
|---|---|
| 目标 | 建立 `ResearchRun`、`KnowledgeUpdateProposal`、Proposal Evidence 与用户决策的权威数据模型 |
| 主要工作 | Alembic migration、ORM、Pydantic DTO、状态机、Repository/Application Service、错误码 |
| 约束 | Proposal 只能草稿/待审；不能直接改 `KnowledgeRevision`；所有关联强制 `space_id` |
| 测试 | 状态迁移、跨空间拒绝、幂等、乐观锁、冻结 Evidence 校验 |
| 提交门槛 | 迁移回放、单元/集成测试、类型检查通过 |

### 4.2 N2.2 外部搜索与多 URL 来源固化

| 项目 | 内容 |
|---|---|
| 目标 | 提供全局搜索所需的服务端 Search Provider 和多 URL 研究来源入口 |
| 主要工作 | `SearchProvider` Adapter（Grok 优先、可替换）、多 URL 请求/结果模型、选择后复用现有 URL SourceVersion 导入链路 |
| 约束 | 密钥仅服务端；搜索摘要不是 Evidence；仅用户选中的 URL 创建来源；SSRF、大小、超时、重定向限制沿用 URL 导入规则 |
| 测试 | Provider 成功、超时、429、5xx、协议错误；私网/重定向拒绝；部分 URL 失败不影响其他项 |
| 提交门槛 | 不泄漏密钥；真实/假 Provider 皆能被契约测试覆盖 |

### 4.3 N2.3 新旧知识比对与 Proposal 生成

| 项目 | 内容 |
|---|---|
| 目标 | 将已固化的新来源与范围内既有 Revision/Evidence 进行可信对比，产出可审核 Proposal |
| 主要工作 | 复用 Hybrid RAG、构建确定性 candidate set、结构化比较 Schema、Evidence 验证、Proposal 草稿持久化 |
| 约束 | 输出支持、补充、冲突、过时、重复或证据不足；每项必须指向本次 Context Evidence；不能支持则保守输出 |
| 测试 | 支持/冲突/过时/无证据样本；范围越界为 0；伪造 Evidence 被拒绝 |
| 提交门槛 | 研究评测最小集、服务端验证和可追踪模型/Prompt/检索版本 |

### 4.4 N2.4 Proposal 审核与 Revision 应用

| 项目 | 内容 |
|---|---|
| 目标 | 用户批准 Proposal 后创建新 Revision、Evidence、事件和索引任务 |
| 主要工作 | 审核 API、应用事务、reconciliation、Activity/Audit、Outbox 索引；前端 Proposal 列表、详情、证据对比和审批 UI |
| 约束 | 审批前 Revision 不变；批准不覆盖历史；拒绝不写知识；相同幂等键可重放；批准前重新验证 Evidence 和目标版本 |
| 测试 | 重复批准、目标被修改、Evidence 失效、事务失败回滚、刷新恢复、焦点管理 |
| 提交门槛 | E2E：来源 → Proposal → 批准 → 新 Revision → 可检索/可引用 |

### 4.5 N2.5 全局悬浮搜索 UI

| 项目 | 内容 |
|---|---|
| 目标 | 建立资料研究入口，不改变知识树内部搜索职责 |
| 主要工作 | 可访问 Dialog/Combobox、查询输入、来源结果、URL 批量输入、选择、研究进度和错误反馈 |
| 约束 | 结果不能直接展示为知识结论；选中后进入来源/Proposal 工作流；键盘可打开、关闭和恢复焦点 |
| 测试 | 组件键盘交互、加载/空/错误、选中资料、无障碍语义 |
| 提交门槛 | 浏览器验证与相关组件测试通过 |

## 7. N4：FSRS、学习计划与掌握度

### 6.1 N4.1 FSRS Scheduler Adapter

- 引入版本化 `ReviewScheduler` 接口和 FSRS 实现；
- 保存状态、参数、算法版本、ReviewLog 和可解释的到期原因；
- 从现有 ReviewCard 平滑迁移，保留简化调度回滚路径；
- 验收：相同日志可重放同一结果，旧卡不会丢失或重复到期。

### 6.2 N4.2 今日学习与学习计划

- 建立 LearningGoal、LearningPlan、PlanItem；
- 以到期复习、待审核知识更新、目标范围和可用时间构建任务；
- Agent/模型只生成可编辑的任务组合与解释，不能修改 FSRS 事实；
- 验收：计划与原始任务可追溯；用户调整后不破坏调度日志。

### 6.3 N4.3 掌握度投影

- 从 ReviewLog、PracticeAttempt 和 AssessmentAttempt 计算主题/知识点掌握度；
- 保存计算窗口、输入记录、算法版本和时间；
- 验收：投影可通过原始日志重算；缺乏数据时展示不确定性，不伪造精确分数。

## 8. N5：练习、考试与面试

| 子任务 | 交付 | 约束 |
|---|---|---|
| N5.1 | PracticeSet、PracticeItem、Attempt 与题目生成 | 题目绑定知识范围、Revision、Evidence 和 rubric |
| N5.2 | 选择、填空、简答、默写作答 UI | 保存草稿、提交、失败重试和可访问性 |
| N5.3 | 基于要点覆盖的结构化评分 | 不能只字符串匹配；无 Evidence 进入人工复核 |
| N5.4 | AssessmentSet、难度递进组卷和成绩记录 | 分数、题型、范围与评分版本可追溯 |
| N5.5 | 面试题组与语音转文字输入 | 仅文本/转写；不做情绪、人格或音频质量判断 |
| N5.6 | 薄弱项诊断与专项补强建议 | 由原始复习/答题记录投影，不让模型改写事实 |

验收闭环：选择范围 → 生成题目 → 作答 → 评分 → 引用反馈 → 保存成绩 → 掌握度变化 → 生成下一步学习建议。

## 9. N6：受控单 Agent

只有 N2 的确定性 Proposal 流程稳定并且确实出现多轮研究需求后启动。

| 子任务 | 交付 | 硬性边界 |
|---|---|---|
| N6.1 | Tool Registry、工具 Schema、权限与审计 | 白名单、scope、超时、调用次数、输出验证 |
| N6.2 | 单 Agent 研究运行与步骤记录 | 只能读来源/知识/证据、搜索 Provider、创建 Proposal 草稿 |
| N6.3 | 多轮补证、停止规则与失败恢复 | 有总调用/Token/时间上限；无证据安全停止 |
| N6.4 | 需要时局部 LangGraph 评估 | Checkpoint 只存运行状态；业务审批仍在 PostgreSQL |

禁止 Agent 直接创建/覆盖 Revision、接受 Candidate、批准 Proposal、删除资源、执行 Shell/SQL、访问任意 URL 或持有长期凭据。

## 11. 固定工作规则

1. 一个独立功能完成后，先运行其聚焦测试、静态检查和差异审查，再提交并推送。
2. 不提交 `.claude/`、本地生成的 Next 类型文件、临时评测报告、密钥或本地 fixture map。
3. 修改 API 契约后按 FastAPI → OpenAPI → TypeScript 方向生成并检查，不手工修改生成物。
4. 所有新写接口有幂等、空间校验、错误 envelope 和审计考虑。
5. 任何模型能力先写固定输入/输出 Schema、业务验证与失败策略，再接入 UI。
6. 不因引入 Grok、FSRS、语音转写或 Agent 而绕过现有 Evidence、Revision、Citation 和用户审批边界。
