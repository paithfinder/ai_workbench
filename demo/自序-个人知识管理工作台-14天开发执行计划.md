# 自序 · 个人知识管理工作台 14 天开发执行计划

> 计划版本：v1.0  
> 编制日期：2026-07-30  
> 需求基线：`自序-个人知识管理工作台-需求开发文档.md`  
> 技术基线：`自序-个人知识管理工作台-技术方案实现文档.md`  
> 原型基线：`index.html`  
> 开发模式：个人主导、每天约 12 小时、4～6 个 AI 编码会话并行  
> 交付目标：个人真实可用的可信知识管理系统，并包含“自适应可信 RAG”和“知识证据审查 Agent”

---

## 1. 最终交付目标

14 天结束时，系统必须可以由个人真实使用，而不是只展示 Mock 数据：

1. 导入真实 PDF、Markdown、TXT、网页和粘贴文本；
2. 保存原始来源及不可变版本，服务重启后数据不丢失；
3. 使用 Docling 解析章节、段落、页码和证据锚点；
4. 使用真实模型生成结构化知识候选；
5. 用户可对照原文编辑、接受、待验证或拒绝候选；
6. 只有接受后的内容进入正式知识树和复习系统；
7. 使用 PostgreSQL FTS + pgvector 进行范围过滤的混合检索；
8. 使用 RRF 融合和 Cross-Encoder Reranker；
9. 自适应可信 RAG 可判断证据是否充分、改写查询、重试检索、拒绝无证据问题并校验引用；
10. 知识证据审查 Agent 可检查重复、矛盾、过时或证据不足的知识，并在人工审批后创建修订候选；
11. 支持基础间隔复习、今日任务和学习记录；
12. 具备最小但真实的 RAG/Agent 评测、Trace、错误处理、备份和 Docker 一键启动能力。

### 1.1 交付定位

最终版本定位为：

> **单用户、个人真实可用、作品集级高质量版本。**

它不是多人 SaaS 生产版，不承诺企业级高并发、组织权限和跨区域灾备，但核心数据、AI 链路和引用必须真实、持久、可测试、可恢复。

### 1.2 两个智能功能

#### 自适应可信 RAG

普通 RAG 搜一次就回答；该功能会：

- 解析用户选择的知识树范围；
- 混合检索并重排证据；
- 判断证据是否充分；
- 证据不足时自动改写查询并重试，最多 2 次；
- 仍无证据时明确拒答；
- 生成后验证引用的 ID、范围、版本和 Claim 关联；
- 引用可修复时最多修复 1 次，否则标记待复核。

#### 知识证据审查 Agent

它是知识库质检员，会：

- 接收用户指定的审查目标和知识树范围；
- 制定简短检查计划；
- 自主调用知识搜索、证据读取、关联查找和版本比较工具；
- 查找重复、矛盾、过时或证据不足的知识；
- 生成修订建议；
- 暂停等待人工批准；
- 批准后只创建“修订候选”，绝不直接覆盖正式知识。

## 2. 本期范围与明确不做项

### 2.1 本期必须实现

- 单用户、本地或个人服务器运行；
- 一个真实知识空间“我的知识库”；
- PDF、MD、TXT、网页和粘贴文本；
- 文本型 PDF 稳定支持，扫描 PDF 提供 OCR 尝试和失败提示；
- 不可变 SourceVersion；
- AI 提炼 + 人工审查；
- 知识树浏览、搜索、来源抽屉；
- FTS + pgvector + RRF + Reranker；
- 自适应可信 RAG；
- 知识证据审查 Agent；
- 简化间隔复习和学习记录；
- 最小评测、Trace、测试和 Docker Compose。

### 2.2 本期不实现

- 多用户注册、组织、分享和复杂 RBAC；
- 多知识库真实隔离和切换；
- Coding 工作台；
- Qdrant、OpenSearch、Neo4j、Temporal、Kubernetes；
- 多 Agent 协作；
- 完整 LangMem 长期记忆；
- MCP 外部工具网关；
- 完整端云双向同步；
- 企业级审计、灾备和生产 SLA；
- 原生移动应用；
- 大规模知识图谱和 GraphRAG；
- 自动修改或删除正式知识。

### 2.3 延误时的降级顺序

如进度落后，按以下顺序降级：

1. Phoenix 可视化改为结构化 Trace JSON；
2. Agent 页面动画和复杂执行时间线；
3. 扫描 PDF OCR，只保留文本型 PDF；
4. 网页动态渲染，只保留静态网页抓取；
5. 学习记录图表，只保留事件列表和统计数字；
6. Reranker 本地部署改为可替换 API Adapter。

以下能力不可降级或删除：

- 真实文件解析；
- 真实 AI 提炼；
- 人工审查；
- 真实检索；
- 范围过滤；
- 服务端引用校验；
- 数据持久化；
- 最小评测；
- Docker 一键启动。

如果 D10 前核心 RAG 仍不稳定，暂停 Agent 开发，先保证 RAG、引用和评测可靠；Agent 可延后 2～3 天完成。

## 3. 最终技术栈

### 3.1 前端

| 技术 | 用途 | 实施约束 |
|---|---|---|
| Next.js App Router + React + TypeScript | Web 应用、路由和页面 | 锁定开发时的稳定版本 |
| TanStack Query | API 数据、缓存和失效 | 服务器事实不复制到全局 Store |
| Zustand 或 React Reducer | 树展开、抽屉、临时 UI 状态 | 仅保存页面交互状态 |
| React Hook Form + Zod | 候选编辑、导入和 Agent 审批 | 前后端 Schema 规则保持一致 |
| React Aria/Headless 组件 | Dialog、Focus、可访问组件 | 来源抽屉和审批弹窗必须恢复焦点 |
| CSS Variables + CSS Modules | 复用 HTML 原型视觉 | 延续原型的来源/AI/正式知识身份颜色 |
| Vitest + Testing Library | 组件测试 | 重点覆盖 Tree、审查表单和回答身份 |
| Playwright | 端到端测试 | 覆盖完整知识闭环与 Agent 审批 |

### 3.2 后端与数据

| 技术 | 用途 | 实施约束 |
|---|---|---|
| Python 3.12+ | 后端和 AI 主语言 | 使用 `uv` 和锁文件 |
| FastAPI + Pydantic v2 | API、SSE、数据 Schema | Router 不写核心业务逻辑 |
| SQLAlchemy 2 + Alembic | ORM、事务和迁移 | 所有 Schema 变化必须有 Migration |
| PostgreSQL + `ltree` + pgvector | 业务事实、树结构、全文和向量索引 | PostgreSQL 是唯一业务事实源 |
| MinIO/S3 Storage Adapter | 原始文件和解析产物 | 本地开发也通过 Adapter 访问 |
| Celery + Redis | 解析、Embedding、索引和批处理 | Redis 不保存最终业务状态 |
| PostgreSQL Job 表 | 任务进度和错误 | UI 只查询 Job 表，不依赖 Celery Result Backend |
| Docling | PDF/文档解析和结构化 Chunk | 保留原始解析产物和 Parser Version |
| httpx + Readability/正文提取器 | 静态网页抓取 | SSRF、超时、大小和重定向限制 |

### 3.3 AI、RAG 与 Agent

| 技术 | 用途 | 实施约束 |
|---|---|---|
| Claude 官方 Python SDK | 知识提炼、回答、证据判断和 Agent 推理 | 使用官方 SDK，不使用兼容代理层 |
| `claude-opus-5` | 首期质量基线 | 通过 AI Gateway 配置，不散落模型 ID |
| Pydantic Structured Output | 候选、回答和 Agent 计划 | Schema 正确不等于事实正确，仍需业务校验 |
| BGE-M3 | 中文/多语言 Embedding | 通过 Embedding Adapter；可本地或独立服务 |
| bge-reranker-v2-m3 | Cross-Encoder 重排 | 超时后降级到 RRF 结果 |
| LangGraph | 自适应可信 RAG 与证据审查 Agent | 不承载导入、审查、知识树和复习业务状态 |
| PostgreSQL Checkpointer | Graph Checkpoint 和跨请求恢复 | Checkpoint 不是正式知识事实源 |
| 自定义 Tool Registry | Agent 工具、权限、超时和审计 | 写操作默认需要审批 |

### 3.4 观测、评测和交付

| 技术 | 用途 | 实施约束 |
|---|---|---|
| OpenTelemetry + OpenInference | LLM、Retriever、Tool Trace | 敏感原文默认不写 Trace |
| Phoenix（时间允许） | Trace、Dataset 和 Experiment | 未接入时必须保留本地结构化 Trace |
| pytest + Testcontainers | 后端、数据库和集成测试 | 使用真实 PostgreSQL/Redis 测试 |
| 自定义 Eval Runner | RAG/Agent 离线回归 | 一条命令生成 JSON + Markdown 报告 |
| Ruff + mypy/pyright | Python 质量 | CI 阻止明显类型和格式错误 |
| ESLint + TypeScript | 前端质量 | 禁止忽略关键类型错误 |
| Docker Compose | 一键启动 | PostgreSQL、Redis、MinIO、API、Worker、Web |
| GitHub Actions 或等价 CI | 自动验证 | Migration、测试、Build、Eval Smoke |

## 4. 架构和职责边界

```text
Next.js Web
   │ REST / SSE
   ▼
FastAPI Application Layer
   ├─ Source / Knowledge / Review / Activity 普通业务服务
   ├─ Trusted RAG LangGraph
   ├─ Evidence Audit Agent LangGraph
   └─ Job API
          │
          ├──────── PostgreSQL + pgvector + ltree
          ├──────── MinIO / S3
          └──────── Redis → Celery Workers
                          ├─ Docling
                          ├─ Chunk / Embedding / Index
                          └─ AI Extraction
```

### 4.1 权威状态归属

| 数据 | 权威存储 |
|---|---|
| 来源、版本、段落和 Chunk | PostgreSQL + 对象存储 |
| 候选、审查决定和正式知识 | PostgreSQL |
| 知识树、证据、复习和学习事件 | PostgreSQL |
| Job 进度和错误 | PostgreSQL Job 表 |
| Celery 消息 | Redis，仅执行调度 |
| RAG Turn 和最终答案 | PostgreSQL |
| Agent Run、Proposal 和审批结果 | PostgreSQL |
| LangGraph 中间执行状态 | PostgreSQL Checkpointer |
| Trace 和 Eval | Phoenix/文件 + 核心摘要写 PostgreSQL |

### 4.2 LangGraph 使用边界

LangGraph 只用于：

1. 自适应可信 RAG 的条件分支、检索循环和引用修复；
2. 知识证据审查 Agent 的动态工具调用、循环、Checkpoint 和人工审批。

LangGraph 不用于：

- 文件上传和解析；
- Candidate 业务审查；
- 知识树 CRUD；
- 复习调度；
- Activity Event；
- 权限和数据库事务。

14 天版本建议控制在以下表：

```text
sources
source_versions
source_sections
retrieval_chunks
extraction_jobs
extraction_candidates
candidate_reviews
knowledge_nodes
knowledge_revisions
knowledge_evidence
qa_sessions
qa_turns
qa_retrieval_hits
qa_citations
review_cards
review_logs
activity_events
jobs
agent_runs
agent_proposals
agent_tool_calls
```

关键约束：

- 所有业务表预留 `workspace_id`，当前固定为“我的知识库”；
- `source_versions` 进入 Ready 后不可覆盖；
- `retrieval_chunks` 使用内容 Hash + Index Config Version 去重；
- Candidate 接受接口使用 Idempotency-Key；
- 知识编辑创建 `knowledge_revision`，不覆盖历史正文；
- Evidence 指向明确的 SourceVersion 和 Section；
- QA Citation 只能引用当前 Turn 实际使用的 Evidence；
- Agent 只能创建 Proposal，不能直接修改正式知识。

## 6. 两个 LangGraph 流程

### 6.1 自适应可信 RAG 图

```text
START
  → resolve_scope
  → hybrid_retrieve
  → rerank
  → grade_evidence
      ├─ sufficient → build_context
      ├─ insufficient 且 attempts < 2 → rewrite_query → hybrid_retrieve
      ├─ empty → abstain
      └─ attempts_exhausted → insufficient_evidence
  → generate_structured_answer
  → validate_citations
      ├─ valid → persist_answer
      ├─ repairable 且 repair_attempts < 1 → repair_answer → validate_citations
      └─ invalid → mark_needs_review
  → END
```

硬性终止条件：

- 检索最多 3 轮（初始 1 次 + 改写 2 次）；
- 回答修复最多 1 次；
- 单次 Turn 总 Token、总耗时和检索数量有限制；
- 范围为空时不调用生成模型；
- 无有效引用时不能把事实性回答标记为可信完成。

### 6.2 知识证据审查 Agent 图

```text
START
  → analyze_goal
  → create_plan
  → select_next_action
      ├─ search_knowledge
      ├─ retrieve_evidence
      ├─ find_related_knowledge
      ├─ compare_source_versions
      └─ check_duplicate_knowledge
  → evaluate_findings
      ├─ need_more 且 tool_calls < 10 → select_next_action
      ├─ sufficient → synthesize_proposal
      └─ limit_reached → synthesize_partial_proposal
  → human_approval (interrupt)
      ├─ reject → persist_rejection → END
      ├─ edit → revise_proposal → human_approval
      └─ approve → create_revision_candidate → END
```

硬性安全规则：

- 最多 10 次 Tool Call；
- 最多 2 次 Proposal 修改；
- Tool 必须经过服务端权限和 Scope 校验；
- Agent 不能调用任意 SQL、Shell、文件写入或删除工具；
- Agent 不直接接受知识点、不覆盖 Revision、不删除来源；
- 审批状态同时写业务表，不能只存在 Checkpoint。

## 11. 多 AI 会话协作规则

### 11.1 会话划分

| 会话 | 职责 | 可修改范围 |
|---|---|---|
| A：集成架构 | Schema、OpenAPI、Migration、公共接口、合并 | 公共契约和基础设施 |
| B：文档知识 | Source、Parse、Extraction、Knowledge | 对应后端模块 |

| D：前端 | 页面、组件、客户端状态和 E2E | `apps/web` |
| E：质量交付 | Docker、CI、安全、测试、README | `infra/`、`tests/`、`docs/` |

### 11.2 强制规则

1. 初始化 Git 后，每个并行会话使用独立 Branch/Worktree；
2. 一个文件同一时间只能由一个会话拥有；
3. 公共 DTO、Migration 和依赖文件只由集成会话修改；
4. 每个任务开始前明确输入、输出、允许修改目录和验收命令；
5. 每个小功能必须同时提交测试；
6. 禁止未经讨论增加框架、数据库或新基础设施；
7. 禁止 AI 为了让测试通过而删除断言、跳过错误或硬编码 Demo 答案；
8. 禁止在前端暴露模型 Key、数据库凭据和对象存储长期凭据；
9. 禁止将模型输出直接拼入 HTML；
10. 每日收尾必须更新进度表、已知问题和下一日阻塞项。

## 12. Definition of Done

任何功能只有同时满足以下条件才算完成：

- 真实数据链路可运行，不依赖硬编码答案；
- 数据有明确的持久化和重启恢复行为；
- API、Schema 和错误码稳定；
- 处理成功、空、失败和重试状态；
- 需要幂等的操作通过唯一约束或 Idempotency-Key 验证；
- 需要范围的操作经过服务端 Scope 校验；
- 模型输出经过 Schema 和业务事实校验；
- 有对应单元/集成/E2E 测试；
- Trace 或日志可定位失败节点；
- README/接口文档同步更新；
- 不包含明文 Secret、跳过测试或未说明的 Mock。

## 13. 关键验收用例

### 13.1 文档与知识闭环

1. 上传真实中文 PDF；
2. 解析出页码、章节和段落；
3. AI 生成带真实 Evidence ID 的候选；
4. 用户编辑并接受；
5. 只创建一个正式知识点、Revision、Evidence 和复习卡；
6. 来源更新创建 v2，旧知识仍指向 v1。

### 13.2 自适应可信 RAG

1. 精确关键词问题一次检索回答；
2. 同义改写问题通过语义检索命中；
3. 初次证据不足时自动改写并重试；
4. 当前文件夹无证据、其他目录有证据时仍拒答；
5. 模型生成不存在 Evidence ID 时被服务端拦截；
6. 引用修复失败时标记待复核，不伪装为可信答案；
7. SSE 断开后可按 Turn ID 查询最终状态。

### 13.3 知识证据审查 Agent

1. 检测语义重复知识点；
2. 检测结论冲突并列出各自来源；
3. 检测引用旧版本或证据不足；
4. 达到工具调用上限后生成部分结果并停止；
5. 服务重启后恢复到人工审批；
6. 拒绝审批不创建修订候选；
7. 批准后只创建 Candidate，不修改正式 Revision；
8. Agent 不能访问范围外知识或执行未注册工具。

### 13.4 复习和活动

1. 未显示答案不能评分；
2. “忘记了”在本轮队尾再次出现；
3. 其他反馈更新下一次复习时间；
4. 重启后队列和日志仍存在；
5. 导入、审查、问答、复习和 Agent Proposal 均形成事件。

## 18. 预估与最终建议

在每天约 12 小时、4～6 个 AI 会话并行、严格目录所有权和每日两次集成的前提下：

- 14 天完成个人真实可用版的可行度约为 **75%～85%**；
- 推荐预留 **2～3 天风险缓冲**，即内部目标 14 天、可靠承诺 16～17 天；
- 最大风险不是代码生成速度，而是复杂 PDF、中文检索质量、模型输出校验、并行合并和端到端稳定性；
- 任何时候都应优先保证真实 RAG、引用、评测和数据可靠性，再增加 Agent 展示能力。

完成后，项目可准确描述为：

> **基于 FastAPI、PostgreSQL/pgvector、Docling 和 LangGraph 的可信个人知识管理平台，实现真实文档解析、AI 结构化知识提炼与人工审查、知识树范围 Hybrid RAG、RRF 与重排、服务端引用校验、间隔复习，以及支持动态工具调用、Checkpoint 和人工审批的知识证据审查 Agent；配套版本化 RAG/Agent 评测与可观测链路。**
