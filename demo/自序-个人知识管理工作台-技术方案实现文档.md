## 1. 架构结论

“自序”采用模块化单体：业务事实、权限、审批、Revision、Evidence、学习记录和审计均由 PostgreSQL 中的领域模型负责；后台任务通过 Job + Transactional Outbox 协调；AI 仅通过受控 Gateway 访问。

```text
Next.js Web
  │ REST
  ▼
FastAPI Application Layer
  ├─ Source / Parse / Extraction
  ├─ Knowledge Tree / Revision / Evidence
  ├─ Indexing / Retrieval / Trusted QA
  ├─ Research / Update Proposal
  ├─ Review / Practice / Assessment
  ├─ AI Gateway / Tool Registry
  └─ Job / Outbox / Activity / Audit
       │
       ├─ PostgreSQL + ltree + pgvector
       ├─ MinIO（原始来源与解析产物）
       └─ Redis → Celery Workers
```

核心原则：

1. PostgreSQL 是业务事实源；Redis、Celery、模型会话、Agent Checkpoint 和 Trace 都不是权威状态。
2. SourceVersion、ParseArtifact、Evidence 和 KnowledgeRevision 不可被新数据静默覆盖。
3. 范围在数据库检索层通过 `space_id + ltree` 落实，而非只写入 Prompt。
4. 模型只能引用本次 Context 提供的稳定 Evidence 标识；服务端负责 Claim、范围、版本和引用文本校验。
5. 用户审批是正式知识写入边界。Agent 能创建 Proposal，不能直接创建或覆盖 Revision。
6. 核心领域逻辑手写，框架只处理可替换的边缘能力；先用确定性流程，真实复杂度成立后再局部引入 LangGraph。

## 2. 当前实现基线

| 模块 | 已实现能力 |
|---|---|
| 来源与解析 | Source/SourceVersion、不可变对象、Docling ParseArtifact、Section、Quote Hash、稳定深链 |
| 提炼与审核 | AI Gateway、结构化 Candidate、Evidence 校验、审核状态机、事务性接受 |
| 知识树 | PostgreSQL 邻接表 + `ltree`、Revision、Evidence、搜索、乐观锁、幂等、软删除 |
| 直接笔记导入 | Markdown/TXT 单文件、多文件和目录导入；不创建 Source/Candidate、不调用 AI，直接创建 document/Revision 并异步索引 |
| 索引与检索 | Chunk、Embedding、Keyword、Vector、范围过滤、检索 debug、评测 fixture |
| 可信 QA | Hybrid RRF、可选 Reranker、有界 Context、结构化回答/拒答、Citation Validation、Turn 持久化 |
| 工程保障 | Alembic、错误 envelope、Job/Outbox、单元测试、检索/QA eval runner、OpenAPI 生成方向 |

因此后续工作不重建 D1–D8 基础，而是复用这些领域服务，补齐研究更新、学习训练与受控 Agent 能力。

## 3. 领域模型扩展

### 3.1 研究与知识更新

```text
research_runs
research_sources
knowledge_update_proposals
knowledge_update_proposal_evidence
knowledge_update_decisions
```

`KnowledgeUpdateProposal` 推荐字段：

```text
id
space_id
target_node_id nullable
target_revision_id nullable
action: create | revise | supersede | merge_suggestion | mark_review_recommended
status: draft | pending_review | approved | rejected | applied | superseded
suggested_title / suggested_body / suggested_tags / conditions / exceptions
comparison_summary
confidence / uncertainty_reason
agent_run_id nullable
model / prompt_version / tool_policy_version
created_at / reviewed_at / applied_at
```

`KnowledgeUpdateProposalEvidence` 关联：

```text
proposal_id
role: new_support | existing_support | conflict | outdated | contextual
source_id / source_version_id / parse_artifact_id / section_id
frozen_quote / quote_hash / locator snapshot
```

应用 Proposal 的事务：

1. 锁定 Proposal 与目标节点，检查状态、范围、版本和幂等键；
2. 重新验证 Proposal Evidence 仍属于所声明的 SourceVersion 与 Section；
3. 根据动作创建 KnowledgeNode 或新的 KnowledgeRevision；
4. 复制/冻结更新后的 KnowledgeEvidence；
5. 将 Proposal 标为 `applied`，保留审批快照；
6. 创建 ActivityEvent、AuditLog 与 Outbox 索引任务；
7. 提交事务。

不允许用 Proposal 覆盖历史 Revision、删除冲突证据或直接修改来源版本。

### 3.2 Markdown 附件

```text
knowledge_attachments
```

建议字段：

```text
id, space_id, revision_id, original_filename,
relative_path, content_type, object_key, content_hash,
created_at, deleted_at
```

约束：

- 附件由特定 Revision 引用，避免文件内容随旧笔记变化；
- Markdown 中的相对图片路径仅能解析到同一导入包的允许资源；
- 首期允许图片存储和展示，不让图片内容作为无证据的文本知识；
- OCR、视觉理解、跨 Revision 附件复用和外链图片抓取后续单独设计。

### 3.3 学习、练习与考试

```text
review_scheduler_configs
learning_goals
learning_plans
learning_plan_items
practice_sets
practice_items
practice_attempts
assessment_sets
assessment_items
assessment_attempts
assessment_scores
mastery_snapshots
```

- `ReviewCard`、`ReviewLog` 是 FSRS 的原始调度事实。
- `PracticeItem` 必须关联考查的 node/revision、Evidence 范围、题型和 rubric 版本。
- `PracticeAttempt`/`AssessmentAttempt` 保存原始作答、语音转写文本、提交时间、评分状态和反馈版本。
- `AssessmentScore` 保存要点覆盖、Evidence 引用、人工调整与模型评分版本。
- `MasterySnapshot` 是可重算投影，保存输入窗口、算法版本和计算时间，不能替代答题/复习原始记录。

## 4. 资料研究与更新架构

### 4.1 搜索与抓取 Provider

```text
Web global search
→ ResearchService
→ SearchProvider (Grok first, replaceable)
→ selected URL ingestion
→ existing Source/SourceVersion pipeline
→ parse / index
→ comparison and proposal
```

Provider 接口应保持窄且可替换：

```python
class SearchProvider(Protocol):
    async def search(self, request: ResearchSearchRequest) -> list[SearchResult]: ...
```

`SearchResult` 只保存发现资料所需的标题、URL、时间、摘要、来源域名与 Provider 元数据。只有用户选择的链接才进入抓取和 SourceVersion 创建，避免将搜索摘要误当作证据。

Grok 凭据只存在服务端。API 调用需保存 request id、provider/model、请求时间、耗时、失败分类和可审计的最小必要摘要，不将密钥或完整敏感上下文写入日志。

### 4.2 URL 安全边界

沿用现有 URL 导入约束并扩展到研究入口：

- 仅允许 HTTP/HTTPS；
- 解析 DNS 和每次重定向后拒绝回环、私网、链路本地与云元数据 IP；
- 限制连接、读取和总超时，限制重定向次数与响应体大小；
- 保存最终 URL、抓取时间、内容 Hash 和响应元数据；
- 失败项逐条报告，不阻断同批其他 URL；
- 外部网页、搜索摘要和抓取内容均为不可信文本，不能改变系统指令、范围或工具权限。

### 4.3 对比与影响分析

```text
new SourceVersion / selected Sources
→ resolve target scope
→ Hybrid Retrieval over confirmed knowledge and evidence
→ deterministic candidate set construction
→ structured comparison generation
→ server-side evidence validation
→ KnowledgeUpdateProposal
```

模型输入只能包含：指定 scope、已确认 Revision 摘要、冻结 Evidence、检索命中和明确的 Proposal Schema。输出动作包括创建、修订、标记复核或合并建议；不允许模型输出数据库写命令。

服务端验证：

- 目标节点、Revision、SourceVersion 和 Section 是否属于同一 `space_id` 与授权 scope；
- 每个支持、冲突或过时判断是否指向本次 Context 中的 Evidence；
- Proposal 是否包含不确定性和反例信息；
- 相同请求/幂等键是否返回已有 Proposal；
- 不能支持的判断降级为“证据不足/需要人工研究”，不进入可应用状态。

## 5. RAG 作为统一证据底座

现有生产 QA 保持以下流水线：

```text
Scope → Keyword/Vector → RRF → optional rerank → bounded context
→ structured answer or abstain → citation validation → persistence
```

研究更新、出题、评分和学习计划统一复用同一范围解析、检索、Evidence ID 和验证逻辑，但业务输出不同：

| 场景 | RAG 输出 | 写入边界 |
|---|---|---|
| 问答 | Claim + Citation 的结构化回答或拒答 | 保存 QA Turn，不修改知识 |
| 研究更新 | 支持/冲突分析 + Update Proposal | 用户批准后由领域服务创建 Revision |
| 题目生成 | 题目、考点、rubric、来源范围 | 保存题目版本，不修改知识 |
| 自动评分 | 要点覆盖、缺失项、引用和置信度 | 保存建议评分；可要求人工复核 |
| 学习计划 | 任务组合、目标说明和建议顺序 | 保存可编辑计划，不修改调度事实 |

共通安全规则：

- RAG 输入的 scope 必须在 SQL/Repository 层过滤；
- Evidence ID 只能来自本次持久化 Context；
- 任何事实性输出必须有至少一个有效 Evidence；
- 无上下文、越范围、引用不存在或引用不完整时拒答/失败关闭；
- 模型输出的 JSON 合法不代表事实成立，必须执行领域验证。

## 6. AI Gateway 与受控单 Agent

### 6.1 模型调用

模型调用继续使用官方 SDK，经内部 AI Gateway 封装 Provider、模型、Prompt、Token、延迟、request id 和失败分类。需要长输出时使用流式响应；结构化输出通过 Pydantic Schema 与业务验证组合保障。

默认质量模型使用 `claude-opus-5`；所有模型变更必须在固定 retrieval/QA/研究数据集上复测，不在领域代码中散落模型 ID。

### 6.2 单 Agent 职责与工具

Agent 仅用于存在动态资料选择、重复补证或多步比较的研究任务。工具 Registry 声明：

```text
name, version, input_schema, output_schema,
required_scope, timeout, max_calls,
risk_level, approval_policy, audit_policy
```

首期只读工具：

```text
search_external_sources
read_source_sections
search_knowledge
read_knowledge_revision
read_knowledge_evidence
compare_source_versions
compare_knowledge_revisions
create_update_proposal_draft
```

`create_update_proposal_draft` 只写草稿 Proposal，不写正式知识。所有工具都由服务端验证 scope、参数、超时、调用次数和审计策略。模型不持有数据库、对象存储、外部搜索或系统执行凭据。

### 6.3 LangChain 与 LangGraph 边界

不以 LangChain 作为项目核心抽象：

- 领域服务、事务、Evidence 校验、Revision、审批、FSRS、评分与审计全部手写；
- 临时 Loader、非核心 Provider 或实验性评测可局部使用 LangChain，但不得泄漏框架对象到领域层；
- 仅当单 Agent 出现多轮工具循环、人工暂停、跨请求恢复、循环补证和明显难以维护的分支时，局部评估 LangGraph；
- LangGraph 的 Checkpoint 绑定 `research_run_id`，只存运行状态；Proposal 审批和正式写入仍由数据库领域状态机控制；
- 多 Agent 不是当前路线，除非有不可由单 Agent 清晰拆分且可独立验证的实际工作负载。

## 7. 长期学习与评分设计

### 7.1 FSRS

通过稳定接口切换调度算法：

```python
class ReviewScheduler(Protocol):
    def schedule(self, card: ReviewCard, grade: ReviewGrade, now: datetime) -> ScheduleResult: ...
```

首期引入 FSRS 时：

- 保存 `scheduler_version`、参数版本、输入状态和输出状态；
- 保留 `ReviewLog` 以便重放、迁移和回滚；
- 仅从已确认、未删除且有有效 Revision 的知识创建卡片；
- Agent 只能说明计划，不得直接重排卡片或写入评分。

### 7.2 题目和评分

题目生成提示词使用冻结的知识 Revision 与 Evidence 范围，输出必须包括题干、类型、难度、考点、标准答案、rubric 和可引用 Evidence ID。

评分流程：

```text
Attempt
→ normalize text / optional speech-to-text result
→ retrieve bound knowledge and evidence
→ structured rubric evaluation
→ validate citations and score bounds
→ persist suggested score / feedback
→ optional user confirmation
→ mastery projection
```

约束：

- 语音转写是输入适配器，不将原始音频分析结果伪装为知识掌握度；
- 评分不能依靠简单字符串匹配；应根据 rubric 要点覆盖、错误类型和范围 Evidence；
- 引用不足、题目基准已失效或模型不确定时进入 `needs_review`；
- 成绩趋势和薄弱项从原始复习/答题记录计算，并显式标注算法版本与置信度。

## 8. API 与异步任务

建议新增端点：

```text
POST /api/v1/knowledge-spaces/{space_id}/research/search
POST /api/v1/knowledge-spaces/{space_id}/research/sources
POST /api/v1/knowledge-spaces/{space_id}/update-proposals
GET  /api/v1/knowledge-spaces/{space_id}/update-proposals
GET  /api/v1/knowledge-spaces/{space_id}/update-proposals/{proposal_id}
POST /api/v1/knowledge-spaces/{space_id}/update-proposals/{proposal_id}/approve
POST /api/v1/knowledge-spaces/{space_id}/update-proposals/{proposal_id}/reject
POST /api/v1/knowledge-spaces/{space_id}/learning-plans

POST /api/v1/knowledge-spaces/{space_id}/practice-sets
POST /api/v1/practice-attempts/{attempt_id}/submit
POST /api/v1/knowledge-spaces/{space_id}/assessments

```

所有写接口遵守已有规范：

- Pydantic 请求验证与统一 `AppError` envelope；
- `Idempotency-Key`、请求 Hash 和乐观锁；
- `space_id` 和目标资源所属空间的服务端校验；
- 返回可 reconciliation 的结果或 Job 状态；
- 业务写入与异步解析、索引、提炼、研究任务通过 Outbox 原子投递。

## 9. 测试与评测

| 层级 | 重点 |
|---|---|
| Domain unit | Proposal 状态迁移、FSRS 调度、rubric 分数边界、Evidence/Revision 规则 |
| Application integration | Proposal 应用事务、幂等重放、冲突、索引 Outbox、跨空间拒绝 |
| Provider tests | Grok/Search Adapter 成功、超时、429、协议错误与密钥隔离 |
| Retrieval/QA eval | Citation Validity、Claim Coverage、Correct Abstention、Scope Leakage、运行元数据一致性 |
| Research eval | 新旧内容支持/冲突/过时判断、Proposal Grounding、无证据保守率、越权率 |
| Learning eval | 调度可重放、题目 Evidence 绑定、评分 rubric 一致性、掌握度投影可重算 |
| Frontend | 全局搜索可访问性、审批焦点恢复、Markdown 导入模式、练习作答和失败/重试状态 |
| E2E | 搜索/URL → 来源 → Proposal → 审批 Revision → 索引 → QA → 复习/练习结果 |

新能力的成功指标优先观察正确性和安全性：范围越界为 0、审批前正式知识变更为 0、无效引用不发布、Proposal 证据覆盖率、正确拒绝率和可重放调度比例。模型输出质量指标必须基于真实冻结测试集，不能预填理想数值。

## 10. 安全、可靠性与演进约束

- 外部搜索、网页、来源文本、模型输出和语音转写都视为不可信输入；
- Agent 工具最小权限、固定 allowlist、严格 timeout 和调用上限；
- 外部请求失败可降级为显示资料不可用，不能自动切换到无来源的模型结论；
- Source/Revision 删除使用软删除与历史快照策略；
- 观测数据默认不写原文和密钥，使用 ID、Hash、采样和脱敏；
- Node/Revision/Proposal 变更有 ActivityEvent 与 AuditLog；
- 不因后续引入 LangGraph、FSRS 或新搜索 Provider 破坏现有 D1–D8 的 API 契约和证据边界。

最终技术路线是：以已交付的可信 RAG 和知识版本体系为底座，先增加人工审批的研究更新与确定性学习能力，再在需要多步研究时局部引入受控单 Agent。
